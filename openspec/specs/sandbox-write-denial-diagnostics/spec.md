# sandbox-write-denial-diagnostics Specification

## Purpose

在 OS 级沙箱拒绝 bash 写操作时，向 agent 和用户提供明确的沙箱归因诊断与授权体验，使被拦截的写不再表现为无法理解的内核原生报错（如 `Read-only file system`），并保证诊断通道不放松任何沙箱策略。

## Requirements

### Requirement: 被拒写操作产生沙箱归因说明

当沙箱已启用且沙箱化 bash 命令的输出包含 OS 文件系统拒绝错误时，系统 SHALL 在返回给 agent 的工具结果中附加一段说明，明确该错误由 OS 级沙箱引起（allowWrite 之外的路径被挂载为只读），而非文件系统本身故障。当监控通道提供了被拒路径时，说明 SHALL 列出这些路径。当沙箱未启用或输出不含此类拒绝时，结果 MUST 保持原样，不得附加沙箱归因说明。

#### Scenario: 监控命中并列出被拒路径

- **WHEN** 沙箱启用时一条 bash 命令对 allowWrite 之外的路径执行写操作，且违规监控上报了该命令的被拒写记录
- **THEN** agent 收到的工具结果包含原始命令输出，并附加说明"该错误来自 OS 级沙箱而非文件系统"，说明中列出被拒绝的路径

#### Scenario: 监控不可用时的输出解析兜底

- **WHEN** 违规监控不可用（如内核不支持 seccomp 用户通知——WSL2 内核即如此、或监听失败），但命令输出包含 `Read-only file system`、`Operation not permitted` 等沙箱拒绝错误文本
- **THEN** 系统从输出中识别被拒路径（可识别时），并按与监控通道相同的方式发起允许提示与自动重试；无法识别路径时，至少附加一段不含路径的沙箱归因说明并指引允许路径或改写目标

#### Scenario: 沙箱未启用时不误归因

- **WHEN** 沙箱未启用，且命令输出恰好包含 `Read-only file system`（真实的只读文件系统错误）
- **THEN** 工具结果保持原始输出，不附加任何沙箱归因说明

### Requirement: 被拒路径可交互式允许并自动重试

当沙箱启用、违规记录给出被拒路径、该路径不在 `denyWrite` 中且会话有 UI 时，系统 SHALL 复用现有的写权限提示流程询问用户是否允许该路径。用户选择允许（任一持久级别）时，系统 SHALL 更新沙箱配置并自动重新执行原命令；重新执行产生的全新结果替换原结果返回给 agent。用户中止或提示超时（或无 UI 会话）时，系统 MUST NOT 自动重试，且最终结果 SHALL 携带"路径保持阻止"的说明。

#### Scenario: 允许后自动重试成功

- **WHEN** 用户在写权限提示中选择"允许（本会话）"，且原命令在路径可写后能够成功
- **THEN** 系统刷新沙箱配置并自动重试原命令，agent 收到的是重试后的成功结果，其中不再包含拒绝说明

#### Scenario: 用户拒绝后不重试

- **WHEN** 用户在写权限提示中选择中止，或提示超时
- **THEN** 原命令的失败结果被返回，并附加说明指出该路径的权限提示被拒绝或超时、路径保持阻止，agent 不应盲目重试同一写操作

#### Scenario: 允许后重试仍失败时终止循环

- **WHEN** 路径已被允许并自动重试过一次，但同一命令再次在同一被拒路径上失败（例如 Linux 沙箱无法为尚不存在的文件挂载写权限）
- **THEN** 系统 MUST NOT 对该路径再次自动重试，而是返回一份说明：指出该路径已允许但仍失败、解释沙箱只能为已存在的路径挂载写权限，并指引改为允许已存在的父目录

#### Scenario: 无 UI 会话不弹提示

- **WHEN** headless（无 UI）子会话中命令的写被沙箱拒绝
- **THEN** 不出现交互提示，结果仍附加沙箱归因说明（含被拒路径），供 agent 与上层会话理解失败原因

### Requirement: denyWrite 显式拒绝给出配置指引

当被拒路径命中 `denyWrite` 规则时，系统 MUST NOT 为其弹出允许提示，SHALL 在说明中明确该路径被配置显式拒绝、重试同一写操作将继续失败，并指出需修改沙箱配置（denyWrite）才能解除。

#### Scenario: 全部被拒路径均命中 denyWrite

- **WHEN** 违规记录给出的所有被拒路径都在 denyWrite 中
- **THEN** 不出现交互提示，说明中包含"被 denyWrite 显式拒绝、重试无效、需修改配置"的指引

#### Scenario: 混合路径时先提示可允许路径

- **WHEN** 被拒路径中既有命中 denyWrite 的，也有仅因不在 allowWrite 而被拒的
- **THEN** 系统仅对后者发起允许提示，说明中同时列出全部被拒路径

### Requirement: 诊断通道不改变沙箱策略

违规监控与其派生的说明、路径列表 SHALL 仅用于诊断与提示归因。系统 MUST NOT 因为违规监控的输出而放宽任何沙箱限制；对路径的实际放行 MUST 且只能通过既有的用户确认流程（允许提示或配置变更）完成。

#### Scenario: 监控事件不能替代授权

- **WHEN** 违规监控上报了某个路径的写拒绝事件
- **THEN** 沙箱配置不发生任何变化，后续对同一路径的写仍然被沙箱拒绝，直到用户通过允许提示或配置变更明确放行

### Requirement: 人类直读通道保持原始输出

用户通过 `!cmd` 直读执行的 bash 命令，其输出 SHALL 保持原样呈现给用户，系统 MUST NOT 在其中附加面向 agent 的沙箱归因说明。

#### Scenario: 用户直读命令的输出不被改写

- **WHEN** 用户在会话中执行 `!echo hi > /var/tmp/some-file` 且该写被沙箱拒绝
- **THEN** 用户看到的输出为命令自身的报错，不包含面向 agent 的沙箱归因说明块
