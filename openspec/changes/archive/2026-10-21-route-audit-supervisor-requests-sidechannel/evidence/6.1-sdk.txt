real SDK, no stub: the worker loads the genuine @earendil-works/pi-coding-agent and reads its
createAgentSession/SessionManager/SettingsManager/defineTool directly; `sessionFactory` is NOT injected, so the
production default factory is the code under test. Provider is a local faux provider registered on a real
offline ModelRuntime (`ModelRuntime.create({modelsPath:null, refreshOnCreate:false, allowModelNetwork:false})`
+ `registerNativeProvider` + `setRuntimeApiKey`), with HOME redirected to a temp dir and no auth file, so no
network call, no real credential and no model token is consumed. Observations come only from the payloads the
real SDK hands the provider plus public runtime APIs.

cases (all four pass):
  1. default factory: `read` really reads the temporary evidence file (content observed in the next payload's
     tool result), a `bash` call is REFUSED by the SDK, and the custom submit tool delivers "ALPHA".
     Also proves runtime-only auth (`setRuntimeApiKey` on a runtime-registered native provider, no auth file,
     no env key) and that the borrowed parent runtime is still usable after the side channel disposes.
  2. capability isolation: the live capability declarations observed in the payloads are a subset of
     read/grep/find/ls/submit_audit_supervisor_reply and never include the seeded historical
     toolsAdded ["bash","edit","write"]; a question that needs new authorisation returns kind "error" with
     code "unresolved" (fail closed) and the evidence file is byte-identical afterwards.
  3. duplicate submit in one ask -> fail closed, one "failed" record, NO answer recorded.
  4. cache warming off: one ask costs exactly the 3 scripted provider requests, no replay/fallback request;
     3 generated assistant messages are billed.
