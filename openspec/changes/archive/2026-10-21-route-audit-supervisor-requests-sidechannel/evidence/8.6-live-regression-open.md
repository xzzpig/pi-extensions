## 已定位(实测,来自最新 case 的 pane 与父 session)

根因错误码已拿到:**`context_error: The parent audit context could not be captured; error details omitted.`**
(不是 config_error / session_error / deadline_missing / invalid_ask,也不是 owner 撤销 —— 旁路在创建会话前就失败。)

已用真实父 session JSONL 排除 role 门禁:该 session 的 role 分布是
`{system:1, user:2, assistant:6, toolResult:8}` —— 全部在允许集合内(system 会被剥离)。
容量也已排除:`capacity_exceeded` 会映射成 `context_capacity_exceeded`,而实际是通用 `context_error`。

因此剩余原因在 `captureCompletedAuditContext` 的**工具组完整性判定**:真实 session 里 assistant 可以一次发出
**多个并行 tool call**,其结果返回顺序与调用顺序不一致,现有实现要求"组内结果严格按序(position === 0)",
于是把合法并行调用判成 `out-of-order toolResult` → context_error → 旁路在提问时立即失败 → 精确取消。
这与上一轮能通过的差别在于:那次父会话的工具调用恰好是严格串行的。

## 需要用户/设计裁决的点

design/spec 原文写的是"out-of-order toolResult → context_error",但真实 SDK 的并行工具调用天然会乱序返回。
两条路:

- (A) **按设计从严**:保持实现,改 E2E 让父会话严格串行(不可控,模型可能并行);
- (B) **修订设计**(需重新评审 spec/design):同一个已完成工具组内允许任意返回顺序,只要该组的 call id 集合
  与 result id 集合完全一致、无重复、无孤立、无跨组混入;真正"孤儿/重复/跨组"仍 fail closed。这也是
  D4 想防的错误形态(缺结果、重复、混组),而不是并行调用本身。

我倾向 (B),但它属于**已批准设计的修订**,按目标规则必须先改 spec/design 并重新评审,不能自行放宽。
在裁决前不会改这条判定,也不会再次请求完成。
