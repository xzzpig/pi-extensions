# 设计：子会话的 npm 扩展来源解析

## Context

本地前台和后台原生子代理共用 `packages/pi-subagents/src/runs/shared/child-session.ts` 创建 Pi `DefaultResourceLoader`。前台不自动加载常规扩展，后台按有效配置发现常规扩展；两者都会把显式来源交给加载器。Pi 按规范化路径去重，不能识别两个不同目录里的同名包。见 [提案](proposal.md) 和 [规格](specs/subagent-extension-loading/spec.md)。

## Goals / Non-Goals

- **目标**：在同一个子会话加载入口解决复用和优先级，让被排除的副本连工厂都不执行；用户不需要引入新配置。
- **非目标**：不修改 Pi 的包管理器、npm 临时缓存布局、外部 runner 或远端协议；不尝试替代 Pi 对非 npm 来源、包资源或加载错误的处理。

## Decisions

1. **在加载前解析，只修改子会话看到的来源。** 在共用子会话加载入口、已有能力约束处理之后调用独立的 fork 模块。识别显式列表内的 npm 包名和选择器，对重复选择去重，对同一包不同选择发出诊断。没有此类来源时保持原路径。仅在 `extensionsOverride` 等加载后钩子中过滤是不够的，因为两个扩展工厂已经执行；不采用此方案。
2. **复用前确认身份与版本，不猜测 dist-tag。** 用宿主 Pi 的包管理 API 查询用户级设置中的已安装路径，核对清单包名和版本，再让 Pi 对本地路径只做资源解析，确认至少存在一个可发现的扩展入口，而非把目录的默认入口误当作 npm 扩展。使用现有的 semver 库判断范围；不做额外的 registry 查询。发现全局安装版本与其配置不符、可能被 Pi 的正常发现过程替换时，不复用该路径。未命中时保留原始 npm 来源，让 Pi 自己处理安装、刷新和失败诊断。避免硬编码 `node_modules` 层级或复制 npm 安装逻辑。
3. **在子会话的发现视图里抑制同名扩展。** 使用仅附着于该子加载器的资源收集适配器，将显式选中包的用户级和可信项目级自动扩展候选写入独立集合，不参与路径合并；包设置及其他资源仍交给 SDK 原样处理。SDK 当前没有公开的加载前包级过滤入口。预先改写包设置为 `extensions: []` 会占用被禁用的路径并遮蔽独立路径声明，还会改变仅含元数据的清单如何发现其他资源，因此不采用。将持久安装路径或原始临时来源交回 Pi 作为显式来源，不改写磁盘，也不抑制宿主必需扩展、独立路径或无关包。

4. **在首个模型请求前校验工具，而不是在扩展绑定时校验。** 含显式 npm 来源的子会话完成绑定及 MCP 就绪后，为本会话的首次普通轮次模型流安装检查。与 SDK 缓存预热相同，按请求的会话路由 ID 区分普通轮次与压缩、摘要；后者使用独立 ID，直接转发且不消耗检查。执行检查时，`before_agent_start` 已运行，扩展仍能按原时序注册工具；SDK 原本的模型流入口（含缓存预热）尚未调用。复用既有诊断；缺少必需工具时由原执行路径报告失败，不调用底层模型。校验通过即还原原流函数，不影响后续轮次和非 npm 会话。仅在 `agent_start` 抛出钩子错误不够，因为 Pi 会记录错误后继续请求。

## Risks / Trade-offs

- **SDK 私有收集接缝变化** → 将适配隔离在 fork 模块，并以固定及当前真实 SDK 测试。找不到兼容的收集入口时给出明确诊断，避免后台静默双加载。
- **路径重合与配置资源筛选** → 保留 Pi 的原始发现规则。验收覆盖可信项目同名包、同路径独立声明、仅含元数据的清单和未匹配包。
- **加载失败时看似可降级到旧版** → 保持旧版被排除；验证 Pi 原有错误处理和显式工具缺失诊断，不引入静默版本回退。
- **误将普通 npm 包目录当成 Pi 扩展执行** → 只将有 Pi 扩展资源的匹配安装转换为本地来源。
- **已存在未批准的实现草稿** → 只保留其工作区字节。正式 apply 时按规格逐项审阅、验证并修正，不因草稿存在而认为任务已完成。

## Migration Plan

无需迁移配置或清理缓存。部署后现有 `npm:` 声明按新优先级解析；回滚软件版本即可恢复旧规则，不需还原磁盘设置。
