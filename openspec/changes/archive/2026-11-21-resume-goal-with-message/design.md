# 设计

## Context

`goal-commands.ts` 的恢复命令目前忽略参数；`goal-scheduler.ts` 的 `resume` 在写入活动状态、重置自主运行额度后安排 kickoff。旧轮的中止收尾仍可能通过 `agent_settled` 暂停同一个活动目标。

## Goals / Non-Goals

只在既有命令和恢复调度入口增加带正文分支。无参命令、Esc 路由、恢复准入和普通用户轮次的后续调度保持不变。不引入队列、定时器、持久化字段或新的调度状态，不修改 Pi 宿主。

## Decisions

- 复用已有目标选择流程；正文非空白时，在命令内使用 Pi 的 `ctx.waitForIdle()` 等待旧轮，并用已有会话身份和焦点操作令牌复核目标。走选择器时，在确定焦点的同步代码段记录这两项，而不是等选择器返回后再读取焦点。等待后在命令的同一同步执行段重新对账、校验身份、恢复并发出正文，最终校验与恢复之间不再跨越异步边界。不要把 `paused` 或收到 Esc 当作收尾完成，也不要把正文作为 steering 插入旧轮。带正文的命令不为等待持有外层模态；真实的目标选择器继续使用既有模态，普通等待不接管 Esc。等待、监听清理和发送编排留在 fork 模块，上游命令只传入既有选择与恢复回调。
- 给现有 `resume` 一个默认保留 kickoff 的可选参数。带正文时沿用同一次恢复写入，使用既有 `idle` 调度相位，不登记 kickoff 决策；恢复成功并记录现有事件后，用 `pi.sendUserMessage` 发送一次正文，不展开其中的命令。比起先排 kickoff 再尝试取消，这不会让两条启动路径竞争。

## Risks / Trade-offs

- `ctx.waitForIdle()` 无法为正文预留首轮：另一条普通消息可能正在 Pi 预处理，尚未标记忙碌 → 按确认范围，不为并发普通消息保证先后。恢复成功后仍通过 `pi.sendUserMessage` 提交一次；Pi 因竞争拒绝时不新增排队、重发或回滚。此边界不改变已运行旧轮的等待或目标身份校验。

- Pi 的空闲判断与 `agent_settled` 有边界时序差异 → 需要选择目标时，在打开选择器前取得 `ctx.waitForIdle()` 的等待句柄，并在命令范围内临时监听 `before_agent_start`，以便在选择期间有新轮启动时仍能在宿主忙碌时取得其等待句柄。等待到最新轮收尾后才同步复核和恢复，命令退出时注销监听；不会因 `agent_settled` 期间 `isIdle()` 已为真而提前恢复。实际恢复前还要同步复查 `ctx.isIdle()`：新轮在 `before_agent_start` 通知到达前就可能已经标记为忙，此时回到宿主等待，不先写入活动状态。SDK 回归同时检查恢复和正文发送的时序。
- Pi 可能在 `agent_settled` 期间暂存整条命令，Goal-X 无法读取提交时的焦点 → 处理器按收到命令时的焦点和既有选择规则确定目标；宿主分派前的切换不在保护范围内。确定目标后至实际恢复前如发生会话或焦点变化，或恢复被拒绝，则不发正文、不对其他目标操作。
