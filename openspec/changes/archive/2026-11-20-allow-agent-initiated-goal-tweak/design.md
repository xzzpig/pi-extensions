# 设计

## Context

`extensions/goal-drafting.ts` 的 `propose_goal_draft` 目前先要求活动草稿，再根据草稿类型选择创建或调整。手动 `/goal-tweak` 走 `startGoalDrafting`，该函数会登记草稿、清理运行时状态并注入启动消息。模型已在执行回合中时，不需要再模拟一条用户命令或注入启动消息。`TweakReview` 和调整事务已负责有效候选、差异、落盘前比较及结果快照。

## Goals / Non-Goals

- 只在现有工具中增加显式准入分支，后续审核和提交仍走同一条路径。
- 理由是提案元数据，可独立展示和回看，不进入目标字段、验证契约或差异投影。
- 不新建命令、工具、调度器或确认组件，不改变目标文件格式。不允许模型借修订恢复停滞目标，手动修订的目标状态准入不变。

## Decisions

### 1. 显式且绑定当前目标的提案

现有参数保持兼容，新增可选的 `tweak: { goal_id: string, reason: string }`；`objective` 仍然必填。模型先从 `get_goal` 或当前执行上下文读取目标身份，只在需要修改目标、验收条件或实质性重排计划时调用。更新执行提示及工具指引，把「让用户运行 `/goal-tweak`」改为「可以提案，但不能直接改写」，保留任务进度和用户显式要求才改预算的原有约束。

显式分支要求非空理由，并从权威状态校验调用所在执行回合、聚焦 ID、`active` 状态及既有门禁；不选目标、不切换焦点、不覆盖正在进行的用户草稿。无 `tweak` 且没有草稿仍直接拒绝。与根据「有聚焦目标」推断意图相比，显式字段保留旧调用语义，也能在模型读取目标后焦点改变时拒绝误改。与另开工具相比，不需要复制提案参数和确认协议。

### 2. 重用调整事务，不模拟草稿启动命令

在现有工具执行内校验后构造绑定目标的调整提案。复用 `TweakReview`、既有预算和任务规则、审计默认值、确认策略及提交前后的焦点和 revision 保护。普通审核期间使用既有 modal 防护；拒绝、取消、确认失败或确认不可用时不留下新的活动草稿。只有「继续讨论」才需要把模型草稿和理由保留为会话分支中的可恢复草拟状态；后续省略 `tweak` 时沿用原目标和理由，显式更新理由时仍须匹配同一目标，不得替换草稿或重定向。确认和取消按既有草稿清理语义处理。不得为进入新分支而合成用户消息、触发额外回合、重置计费或强行变更调度决策。

自动确认继续调用现有策略，不另设开关。`PI_GOAL_AUTO_CONFIRM=1` 及既有无 UI 默认路径同样构造并提交经过校验的候选；`0` 强制走交互决定，不可用时明确拒绝。自动确认不是绕过过期检查的途径。调用前的拒绝、继续讨论、取消和提交冲突均不得提前写入目标定义或调整账本事件。

### 3. 理由在正文层展示，差异仍只描述实际目标变化

将同一份经过文本净化的理由作为审核展示数据传给确认组件，在可滚动正文的最前面以独立区块渲染；差异和全文及基础 `ui.select` 回退均展示，不侵入共享差异条目或改变现有决策区。结果快照保留每次实际审核的理由和结果，供手动及自动确认回看；旧会话和无理由的手动提案按旧展示渲染。相比拼入 `objective` 或 diff 文本，独立字段不会被当作新的目标要求、丢在富视图只读差异条目之外，或在后续目标变化时被重新计算。

### 4. 控制 fork 分歧

优先扩展 fork 自有的审核与展示模块，并将新准入等逻辑留在 fork-only 模块；上游文件仅保留工具模式、主流程接入及必要提示的最小接缝。实施时按 subtree inventory 确认归属，维护相应同步接缝记录，不格式化上游文件。新增回归测试使用 fork-only 测试文件。

## Risks / Trade-offs

- [确认期间并发切换焦点、修改目标或中断] → 复用既有目标身份、焦点 token 和 revision 提交检查；测试确认不可用及过期时未写入新定义。
- [长理由在窄屏遮住差异，或模型文本携带终端控制字符] → 理由使用现有正文的安全文本处理、换行及滚动机制，基础和富视图均验证，不增加常驻控制行。
- [取消后自动续跑立即再次弹出相同提案] → 工具返回明确的调整取消结果，执行指引要求尊重该决定，不立即重提同一修订；不额外暂停原目标。

## Migration Plan

现有调用无需迁移；不迁移目标文件。模型草稿扩展只使用向后兼容的会话元数据，既有记录无理由时仍可回放。回退版本移除可选提案入口，保留已确认的目标内容及手动 `/goal-tweak`。
