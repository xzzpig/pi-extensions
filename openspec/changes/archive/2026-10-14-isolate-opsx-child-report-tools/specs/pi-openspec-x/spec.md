# Spec Delta

## MODIFIED Requirements

### Requirement: 结构化裁决上报

缺口分析、计划审查、opsx-worker 三类子 agent MUST 各经插件提供的专用上报工具提交结果（缺口分析、计划裁决、完成声明与证据），结果以带 schema 的结构化形式经委派返回；opsx-reviewer 的最终裁决 MUST 经执行底座完成审计的结构化裁决通道提交（verdict 语义映射 APPROVE/REJECT），插件不另设平行裁决通道。门控判断 MUST 依据结构化裁决字段，MUST NOT 依赖解析子 agent 的自由文本；不满足 schema 的上报 MUST 被拒绝。

插件的默认资源配置 SHALL 将 `report_gap_analysis` 仅提供给 `opsx-gap-analysis`、`report_plan_review` 仅提供给 `opsx-plan-review`、`report_work` 仅提供给 `opsx-worker`。主会话、其他子代理及 `opsx-reviewer` MUST NOT 注册这些上报工具，MUST NOT 向其模型暴露这些工具的声明、工具发现条目或专用上报提示词；该隔离 SHALL 在普通会话、计划态、代理实现态、直实现态以及重新加载后的初始化中保持一致，不得通过主会话先注册再隐藏或角色切换时增删来实现。对应子代理的前台与后台原生执行 SHALL 均能加载自己的上报工具，且不得加载其他角色的上报工具。

#### Scenario: 裁决字段驱动门控

- **WHEN** 计划审查的上报工具收到 `verdict: OKAY`
- **THEN** 门控以该结构化字段放行，无需解析文本

#### Scenario: 普通主会话没有子代理上报能力

- **WHEN** 插件在普通主会话初始化或重新加载
- **THEN** 工具注册表及模型提示词中均不存在三个子代理上报工具的声明和专用上报规则，按工具名称直接调用也不可执行

#### Scenario: 模式切换不引入子工具

- **WHEN** 主会话进入 `/opsx:plan` 或任一 `/opsx:implement` 模式
- **THEN** 主会话仍无三个子代理上报工具；计划阶段保留 `opsx_plan_gap_analysis` 与 `opsx_plan_verdict` 的父侧职责

#### Scenario: 各子代理仅取得自己的工具

- **WHEN** 分别以插件默认配置启动 `opsx-gap-analysis`、`opsx-plan-review`、`opsx-worker` 和 `opsx-reviewer`
- **THEN** 前三者各自仅取得自己的一个上报工具，`opsx-reviewer` 不取得这三个工具，并继续使用执行底座的最终裁决与进度通道

#### Scenario: 子扩展不可加载时不回退到主会话

- **WHEN** 对应子代理的上报工具无法加载或被能力限制排除
- **THEN** 子运行明确报告缺少必需工具，主会话不代为注册或代为调用子工具，缺少 worker 报告的任务不得完成

### Requirement: 代理实现模式的沙箱白名单与派发审查

代理实现模式下，主 agent MUST 切入 agent 角色（opsx-agent 沙箱 profile）：文件写入被沙箱 profile 限制在 `openspec/` 目录与构建产物目录（如 node_modules、dist），源码区只读，bash 在同一白名单下运行以支持自跑 build/test 验证。实现 MUST 通过派发全写权限的 opsx-worker 子 agent 逐任务完成，派发提示词 MUST 包含任务、预期产出、所需工具、必须做、禁止做、上下文六个部分，并标识该次派发对应的任务；每次派发返回后，主 agent MUST 审查 worker 全部改动（逐文件读取与 diff 核对，对照其结构化完成声明）并运行验证，通过后才可勾选 tasks.md 对应任务。

worker 的成功结构化报告 SHALL 由插件自动接收；主会话 MUST NOT 转录报告到 `report_work`，插件 MUST NOT 新增 `review_work`、`opsx_review_work` 或等价的独立父侧验收工具。主会话完成实际审查后 SHALL 使用现有 `update_goal_task(status="complete", evidence=...)` 申请任务完成，不改变该工具的参数契约，也不把完整 worker 报告放进简短的 `evidence`。完成申请执行前 MUST 检查当前聚焦目标所属流程、当前任务对应的子运行已经成功结束、有效报告已经接收、验证通过，以及报告与执行窗口改动的核对结果；报告接收本身 MUST NOT 自动完成任务或替代主会话审查。普通目标及主会话直实现模式 MUST NOT 因没有 worker 报告而被此门阻塞，最终独立完成审计保持不变。

#### Scenario: 主 agent 越区写被拒

- **WHEN** 代理实现模式下主 agent 尝试修改源码文件
- **THEN** 写操作被沙箱拒绝，提示应改为派发 worker

#### Scenario: 未审查不得勾选

- **WHEN** worker 返回但主 agent 尚未核对其改动与验证结果
- **THEN** tasks.md 中该任务保持未勾选状态

#### Scenario: 不转录报告也能完成已审查任务

- **WHEN** worker 成功结束并提交有效报告，插件已接收该报告，主会话核对改动并验证通过后调用现有任务完成接口
- **THEN** 完成门使用已接收的报告检查并放行，不要求主会话另行调用任何报告或验收工具

#### Scenario: 收到报告不等于完成任务

- **WHEN** worker 报告已接收，但主会话尚未申请任务完成
- **THEN** 任务状态和 tasks.md 复选框保持原样

#### Scenario: 报告缺失或验证失败时阻塞

- **WHEN** 主会话申请完成任务，但对应子运行仍在执行、报告未接收、报告无效、没有验证记录或验证失败
- **THEN** 在任务状态变更前阻塞并给出对应原因，不指引主会话使用子代理上报工具补交报告

#### Scenario: 报告文件集合保持既有核对策略

- **WHEN** 报告宣称修改了执行窗口中不存在的文件，或窗口中存在未列入报告的其他文件
- **THEN** 前者阻塞完成；后者在排除既有运行时噪声后警告主会话确认归属，保留原有核对策略，不以本变更扩大为全仓审查

#### Scenario: 批量完成不能绕过门控

- **WHEN** 主会话以现有任务工具的批量更新形式同时申请完成多个任务，至少一个完成项不满足报告前提
- **THEN** 在批量操作执行前阻塞整个请求，所有任务均保持原状态；全部完成项符合前提时交由原有原子更新执行

#### Scenario: 直实现与普通目标不受影响

- **WHEN** 主会话直实现模式或普通非 opsx 目标使用任务完成接口
- **THEN** 不要求 worker 派发或报告，仍按既有任务约束及最终完成审计执行，不将普通目标的完成投影为 opsx 任务完成

#### Scenario: 报告刷新期间焦点切换

- **WHEN** 代理实现目标的完成申请等待报告刷新期间，目标焦点或所属分支发生变化
- **THEN** 拒绝这次旧申请并提示按当前焦点重试，不把旧目标的报告用于新目标；新申请若属于普通目标则不要求 worker 报告

#### Scenario: 任务工具逻辑拒绝不能产生假完成

- **WHEN** 任务工具因为缺少 evidence、子任务未完成、任务被禁用或其他约束拒绝更新，即使返回未设置工具错误标记
- **THEN** 插件以实际目标及任务状态是否转换为依据，不发布 task_completed、不把该项记录为已完成

## ADDED Requirements

### Requirement: 子报告自动接收的来源与运行关联

插件 SHALL 从当前主会话拥有的原生子运行取得结构化上报结果，覆盖成功前台结果、后台完成以及工作流中的原生子运行；MUST 验证父会话、当前分支流程、所属目标、子运行身份、角色和 worker 任务身份。后台启动回执、部分输出和进行中的上报 MUST NOT 当作成功结束的交付报告；工具参数显示预览、模型总结、其他自由文本及 best-effort 诊断日志 MUST NOT 作为完整门控报告来源。主会话不得被要求手动调用状态或等待工具来转录报告，插件不得为自动接收另行启动子代理。

同一次运行重复投递的同一报告 SHALL 幂等处理；同一次运行的后续成功上报 SHALL 覆盖早先上报；后续失败、无效或缺少配对结果的上报 MUST 使早先成功不能用于放行。新的任务派发或恢复执行 SHALL 使用新的运行/attempt 身份，使旧成功报告不能替代新运行的交付。报告失败、运行失败、停止、超时、报告无法读取或来源无法关联时 MUST 保持任务未完成并明确诊断。有效报告的来源及接收记录 SHALL 随所属主会话分支持久化；压缩或恢复时 MUST 先重建当前流程与目标的完成门绑定，再恢复有效记录，不得因为进程内状态为空而跳过门控，也不得导入其他分支或旧流程的报告。

自动接收 SHALL 明确支持的协议版本及资源预算；未知版本、超过预算、规范证据不完整或持久化失败时 MUST 明确拒绝用于完成，不静默截断、回退自由文本或无限制扫描。实时进度监听失败时 SHALL 降级显示并保留完成前的有界主动读取，不以通知是否先到作为交付成功条件。

#### Scenario: 后台回执不放行完成

- **WHEN** 主会话收到后台 worker 的启动回执，但该子运行尚未成功结束
- **THEN** 只记录运行身份与进行中状态，任务完成申请被阻塞

#### Scenario: 后台完成后自动摄取

- **WHEN** 本会话拥有的 worker 后台子运行成功结束并存在完整合法的成功上报工具结果
- **THEN** 插件自动接收报告；随后完成申请能够使用该报告，不依赖主会话再次上报或手动查询子运行状态

#### Scenario: 工作流中存在多个子运行

- **WHEN** 同一成功工作流包含多个原生子运行，并分别提交不同任务的报告
- **THEN** 按实际子运行与任务身份分别接收，不能把工作流根回执或某个兄弟子运行的报告用于另一任务

#### Scenario: 失败前台工作流丢失子证据

- **WHEN** 前台工作流根结果失败且原生工具边界未返回可验证的子消息，即使通知声称部分子项成功
- **THEN** 明确报告该次证据不可取得，不登记其 worker 为可完成；后续只能使用新的有效派发证据，不能使用摘要或旧报告补齐

#### Scenario: 其他会话或任务的报告被隔离

- **WHEN** 报告来自其他父会话、其他流程/分支/目标、非对应角色或与派发任务不符的 taskId
- **THEN** 不登记为当前任务的交付报告，不改变任何任务状态

#### Scenario: 失败的上报不算交付

- **WHEN** 上报工具失败、payload 不满足原有 schema，或 worker 的运行最终失败、停止、超时
- **THEN** 不获得可供完成门放行的报告；不能以工具调用参数或早先成功报告掩盖失败

#### Scenario: 诊断日志漏写不掩盖最后一次失败

- **WHEN** 本次运行先成功上报，后续上报失败，而 best-effort 诊断日志漏写了失败事件
- **THEN** 插件仍通过完整规范运行证据识别最新失败或证据缺口，不能以诊断日志中的旧成功报告放行

#### Scenario: 新一轮派发使旧报告失效

- **WHEN** 同一任务已有成功报告，随后又派发或恢复 worker 修改该任务
- **THEN** 完成门等待最新子运行及 attempt 的有效报告，旧报告不能放行该任务

#### Scenario: 冷重启后完成门仍有效

- **WHEN** 主会话冷重启，原有 opsx agent 目标恢复但插件进程内流程和 tracker 均为空
- **THEN** 从当前分支及实际目标重建门控绑定；没有有效交付记录的任务仍被阻塞，不自动选择目标、启动执行或改变任务状态

#### Scenario: 压缩与恢复仅使用当前分支证据

- **WHEN** 会话压缩或恢复后重新检查任务完成前提
- **THEN** 使用所属分支和当前流程/目标的已记录运行及报告身份，无法证明归属的旧报告不被采用

#### Scenario: 完成通知先于完成事件

- **WHEN** 原生通知先唤醒主会话，子完成事件尚未投递，但该所属运行已有完整成功终态和规范报告
- **THEN** 完成门的有界刷新能够取得并登记证据，不必让主会话转录或调用等待工具；若终态/证据仍未齐则明确保持阻塞

#### Scenario: 不兼容或证据超预算

- **WHEN** 运行数据版本不受支持、证据超出已声明预算、路径越界或完整性检查失败
- **THEN** 该报告明确不可用于完成，不回退诊断日志/自由文本，不影响普通目标的原有任务完成行为

#### Scenario: 隔离后进度仍来自实际子报告

- **WHEN** 对应子运行提交带有结构化 progress 的有效报告
- **THEN** 主会话投影实际收到的阶段与百分比，不依赖主模型调用子工具制造进度；进度显示不触发任务完成或替代最终裁决
